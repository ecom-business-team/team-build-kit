# /convert-to-standard

You already have something: a folder of scripts, a workflow that runs every night, a spreadsheet with a process around it, a whole system nobody wrote down. This command looks at what is actually there, names what kind of thing it is, writes exactly the documents the standard says it is missing, and hands it into the lifecycle so the next change to it goes through `/memo` or `/quick-fix` like everything else. It is the way to start from existing work. `/new-workspace` is the way to start something new; both end at the same place.

## Usage

```
/convert-to-standard <folder>                      — a folder on disk
/convert-to-standard <name of a running system>    — something that runs elsewhere (an automation, a hosted service); you say where its parts run
```

---

## Phase 1: Confirm the target and its level

Resolve the target: the folder's path, or the system's name and where each of its parts runs (which host, which automation platform, which database). State it back in one sentence.

Then ask only the **level** questions from `/new-workspace` Phase 1, in the same plain words:
- "Does it hold multiple things you build and run separately, or is it one buildable thing?"
- "Is there ongoing development here, or is it static reference material?" (scripts still in use count as ongoing)
- "Is this one build, or a sequence of milestones that build on each other over months?"

**When the target is the workspace root** (it holds `.claude/kit_receipt`; Phase 3 says what that adds), its level is workspace whatever it holds, so the level questions are not asked for it: state back that it is the workspace root, and that its doc set is its map (`CLAUDE.md`) as the index, the root skeleton, and one `CONTEXT.md` per area inside it (each area's level and kind are read in Phase 2 and stated in the Phase 3 plan for approval), naming the candidate areas, then stop for confirmation; this replaces the level state-back below, and a correction is restated and stopped on again the same way. The candidate areas are the person's own top-level folders, not `.claude/` or a folder whose files are all listed in `.claude/kit_receipt` (one path per line with its sha256; the installer placed those); a folder that only holds other areas (`clients/` holding `clients/acme/`) is not one itself, its children are, and it gets no `CONTEXT.md` and no routing row of its own. Phase 2 sends one ground-truth agent per candidate area, and among the gap questions asks, for each, "Is there ongoing development here, or is it static reference material?" (scripts still in use count as ongoing), and no other level question; whether an area holds several separately built things is read from the observations, not asked, and such an area is stated in the plan as a workspace-level area.

**Do not ask the fork** — this is existing work, so it is brownfield by definition. **Do not ask the kind** — what it is made of is observed in Phase 2, never asked. State back the level with the doc set it implies (`~/.claude/skills/_shared/documentation_standard.md`, Part 2) and stop for confirmation. If the person corrects the level or the scope, restate and stop again.

## Phase 2: Observe, then fill gaps

Run `/new-workspace` Phase 2b exactly as written (`~/.claude/skills/new-workspace/SKILL.md`, Steps 1–3): one ground-truth agent per area the target touches, facts only; reassemble the reports into one verified picture, including what each part is made of at runtime, which is where the kind comes from; then ask the person only what the files and the live system cannot say. Every line you will write must trace to something observed or explicitly confirmed. The steps are not restated here: one method, one place.

## Phase 3: Provision and verify

Run `/new-workspace` Phases 3 and 4 as written: exactly the doc set for the confirmed level and the observed kind, its `CONTEXT.md` with the Kind and Proved-by lines stated (or `not yet stated`, when the proof does not exist yet), canonical homes created if the level needs them, the root `CLAUDE.md` routing row added after approval, never overwriting an existing file. When that root `CLAUDE.md` exists, run `python3 ~/.claude/skills/_shared/map_update.py plan <it>` and put its offer in the plan you show, presented as `/update-build-kit` Step 3 presents it: the offer, the take question, the values, the apply, and naming their duplicate lines (not Step 3's run condition, its "next update" line or its Step 4). Nothing is written before approval, so take the values from the plan's `Values to ask for` line (this replaces Step 3's run-apply-first route), and show the plan in two passes: first the whole Phase 3 plan with the offer in it, and the take question; then, once the person has chosen their sections, ask for each value that line names, as Step 3 asks them (`path, once you have one` is never asked; Step 3 gives its value), and show the full plan, with the answers, for approval. In the trace, the kit's lines come from the kit's template and the values from the person's answers. After approval, apply the sections the person took before adding the routing row. If the command is missing or fails, say so, tell the person that `/update-build-kit` brings the map step, and continue the conversion without it. Before showing the plan, run the trace yourself: beside every line you intend to write, name the file, the observed run, or the person's answer it comes from. Who performs a manual step, who owns the code, whether a file is disposable, what the history was and what checks exist today are facts to observe or to ask, never to infer; a line with no source is cut. Then show the plan and wait for approval.

**When the target is the workspace root**, the plan also creates whatever part of the root skeleton is missing, as `/onboard` creates it for a new workspace. The target is the workspace root when it holds `.claude/kit_receipt`, which the kit's installer writes only into the folder it installed into; an area inside a workspace has no such file, its root already has the skeleton, and none of this applies.
- **What.** Follow `~/.claude/skills/onboard/SKILL.md` Phase 4b step 3 (every root entry of the template library's skeleton, `AGENTS.md` and `.gitignore` from its exact text, `bulk_ops/INDEX.md` from template 4.12, an empty `.gitkeep` in each folder left empty) and step 6 (`SKILLS.md`, with its loop) as written there; they are not restated here. Check each entry on disk. One that already exists (the person's own, or one the installer placed) is kept exactly as it is (an existing folder gets no `.gitkeep`, though a missing folder inside it is created with one) and named as kept in the plan; Safety rule 1's update offer does not apply to it. An entry `/new-workspace` Phase 3 also plans for this root is listed once.
- **The map.** The root's index is its map, `CLAUDE.md`, as `/onboard` makes it: no `CONTEXT.md` is written at the root, and the root carries no Kind line (each area's `CONTEXT.md` does). An area is a folder the person confirms in the plan as one thing they work on; each gets its own `CONTEXT.md`, as `/onboard` Phase 4b step 7 makes it (`/new-workspace` for that folder, brownfield, from Phase 2's observations, without its own state-back, approval or card, which this conversion's plan and card cover; its routing row is the one below), and one routing row in the map's own shape, `| {a task in plain words} | {the folder, and its CONTEXT.md} |`, whose task wording you draft from the observations and the person confirms in the plan; no row points at the root itself. The rows replace the template's example row wherever it stands (with no area, it is deleted; the map step never writes that row or asks for its slots, so in a table without it the rows go first, above `New project`), and the comment line `<!-- The first-run interview fills the table. -->` is deleted; when the person's own map, after the sections they took are applied, has no routing table, the rows go under its `## Routing` heading if it has one, otherwise under a new `## Routing` heading with only the template's table header line and its separator, copied as they are, placed right after the map's `#` title (at the top when it has none). When the root has no `CLAUDE.md`, the plan writes one as `/onboard` Phase 4b step 4 does, with those rows, and no other `/onboard` step runs (not its commit or its closing talks); it asks `/onboard` questions 4, 5 (with its connected-tool check; its labels only when the answer stays an app) and 6 for its values; the map step does not run, since there is no map to offer sections to, so the first pass is the plan alone (it asks nothing, so it does not wait; it shows the map as written from the template, naming the values still to ask, and its rows in full), and the second asks those questions and then shows the full plan with the answers for approval. Where the check says to re-run `/onboard`, re-run `/convert-to-standard`; nothing is written before that.
- **`tasks.md`** (template 4.13) is created only when the person has no task manager this session can write to. When the map step asked for the task manager, or this conversion writes the map, use that answer; an app counts only when this session has a connected tool for it (`/onboard` question 5's connected-tool check, with its two choices; it runs here, although `/update-build-kit` Step 3 skips it). When the map step asked for none (no section the person took needs it, or the command was missing or failed), ask question 5 with that check: the question only, since the three labels are asked only by the map step, for the sections that need them. The first pass shows `tasks.md` as conditional on it. Ask it in the second pass beside the other values, where it may be the only question, or before the full plan when the map step did not run. No task-manager proof runs (not `/onboard` step 5). When `tasks.md` is created, the root had a map before this run, and the person took no section that names the task manager, say in the plan (only there) that their map does not name it yet and that `/update-build-kit` offers those sections again.
- **Order and record.** After approval, create the skeleton (with `SKILLS.md`, and `tasks.md` when it is created) first, then the rest of the Phase 3 plan, then write the map (its rows are in it, so no later step adds them) or apply the sections the person took and then add the routing rows; an existing map changes only by the sections the person took and the routing rows. List every entry created in the plan and in the card's **Written** line, each folder created by its own path (its `.gitkeep` is not listed separately, nor a parent such as `_admin/` created only to hold it).

## Phase 4: Hand off

Before the card, ask the person what they want changed first; their answer names Next (`/quick-fix` when it is a known small defect, otherwise `/memo`). Print the **handoff card** (`documentation_standard.md` §4.10). Its values:
- **Title:** `standalone · {folder}` for any conversion outside an initiative, or `{initiative} · {folder}`, where `{folder}` is the target's path from the workspace root, or the root folder's bare name when the target is the root; no ribbon.
- **Done:** Brought to standard: N areas observed ("one area observed", for a single area). Proved by `index_check.py` exiting 0 for each `CONTEXT.md` written.
- **Next:** `/memo {the first thing the person wants changed}` | `/quick-fix {a known small defect}`, with the line from `python3 .claude/tools/orientation_cost.py --now {memo, or quick-fix when Next names /quick-fix}`, run from the workspace root (the kit's installer places `orientation_cost.py` there, beside the `index_check.py` that `/new-workspace` Phase 4 runs).
- **Filed this session:** every question neither the files nor the person could answer, filed to the task manager the map names that this session can write to (`/onboard` question 5's connected-tool check decides, for any target), including one this run wrote (or `tasks.md`, under `## Next`), with its id; the approved plan says they will be filed there, so filing needs no second approval. When there is neither, those questions go under Needs {owner} instead. A filed task's *Expect* names the person as the Needs heading does.
- **Residuals:** as §4.10 gives them, `None.` when empty; a choice the person made (such as `tasks.md` over connecting an app) is not a residual.
- **Needs {owner}:** only a decision or step the person alone can take. `{owner}` is the name the map gives in "Words the skills use", including one this run wrote; when it gives none, the heading reads "Needs you".
- **Written:** the paths from the workspace root, each folder created by its own path (its `.gitkeep` is not listed separately, nor a parent created only to hold another entry, such as `_admin/` or `bulk_ops/`), and a file created then filed into, such as `tasks.md`, listed once.

Next is always something the person can type verbatim. If nothing needs changing yet, Next is `/memo` for whatever they name first; the docs are now the substrate that command reads.

## Safety Rules

1. **Never overwrite existing files** — check first; offer update-or-skip.
2. **Confirm before writing** — show the Phase 3 plan and wait.
3. **Stay inside the target** — all paths relative to the target's root; the workspace root is touched only for the routing row, the map sections the person took, canonical homes, and, when the target is the workspace root, the missing skeleton entries (Phase 3).
4. **No secrets in generated files** — reference where credentials live, never their values.
5. **Never lower the bar** — a line you cannot trace to something observed or confirmed is cut, not kept.
